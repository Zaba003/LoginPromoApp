# 02. Архитектура: модульный монолит на Cordis

## Решение
Один развёртываемый API-процесс (в перспективе несколько одинаковых реплик) с контролируемым набором Cordis-плагинов. Отдельный React-клиент. PostgreSQL — единственный системный источник истины. Отдельные worker-процессы могут использовать те же доменные модули и очередь, не становясь независимыми микросервисами.

```
[React Web]  [Pulse (позже)]  [внешние системы]
      \      |                  /
        HTTP/API boundary: AuthN -> AuthZ -> REST/OpenAPI
                           |
               Cordis application context
      +--------------------+----------------------+
      | catalog  templates campaigns assignments |
      | submissions approvals metrics aggregation|
      | documents  notifications audit  adapters |
      +--------------------+----------------------+
          ports: database / queue / file-store / identity / exports
                           |
                    PostgreSQL / локальное хранилище
```

## Cordis: ответственность и ограничения
- `Context` — контейнер зависимостей, сервисов и событий; `plugin()` подключает модули.
- Каждая возможность оформляется как **внутренний доменный модуль** или **заменяемый адаптер**.
- У сервиса явный контракт, владельцы данных и методы. Не обращаться к таблицам другого модуля напрямую.
- Горячая замена допустима для **stateless-адаптеров**, только после проверки совместимости; нельзя «выгрузить» транзакционную логику посреди операции.
- Перезагрузка плагина не отменяет согласования, зарегистрированные в БД, и не теряет очередь.
- Плагины загружаются **только из allowlist** пакетов с контролируемыми версиями; никакого произвольного исполняемого кода из пользовательских шаблонов.
- Конфигурация плагина — декларативная, проверенная по схеме, с зафиксированной версией и журналом изменений.

## Границы данных
- Каталог: типы/получатели/версии регламентов.
- Формы: версии схем и пользовательские UI-схемы.
- Кампании: период, дедлайны, задания, статусы.
- Сдачи: данные/версии/вложения, операции отправки и проверки.
- Показатели: определения, единицы, правила, значения с источниками.
- Сводка: снимок входных утверждённых версий и конкретная версия правил.
- Документы: экземпляр, шаблон, бинарный артефакт, контрольная сумма.

## Согласованность
- Изменение статуса сдачи + запись аудита + outbox-событие — в одной транзакции.
- Worker обрабатывает событие **как минимум один раз**, операции должны быть идемпотентными.
- Сборка сводного документа по **snapshot** одобренных данных; если входы меняются — новая версия сводки, а не тихое изменение старой.
- DB-модули мигрируются явным инструментом при обновлении платформы (контролируемые миграции), не при случайной загрузке плагина.

## Правила расширения
- Новый ведомственный экспорт: `export-adapter` с поддерживаемой версией формата.
- Новый источник данных: `source-adapter`, который записывает provenance и проверяет полномочия.
- Новый способ оповещения: `notification-provider`.
- Новая логика вычисления: зарегистрированный проверенный `calculation-provider`, без eval пользовательского текста.
- Независимая юридически значимая передача: `submission-gateway`, только при наличии регламента и аудита подтверждений.

## Технические оговорки
HTTP-слой (Fastify) и ORM (Kysely/Drizzle) ещё не подтверждены тестом совместимости с выбранной версией Cordis. Они не должны попадать в доменные методы. API-стартер специально демонстрирует только жизненный цикл Cordis и endpoint `/health`.
